# 0024. Manifest as an authoring and import format

- **Status:** accepted
- **Date:** 2026-06-18

## Context

The `DataMap` manifest has so far been documented as *derived, never
authored*: the SQLAlchemy adapter's `collect_data_map(metadata)` walks ORM
models, reads the `pii()` / `subject_link()` annotations it finds, and builds
the manifest from them. The serialized payload (`DataMap.to_payload()` /
`DataMap.from_payload()`) was framed purely as a *snapshot* — something you
emit for audit diffing and tooling, then throw away.

Two forces make that framing too narrow:

- **Manifest-driven execution (#71).** Loading a hand-written or
  externally-produced manifest and running export/erasure off it — without a
  live ORM registry — is a first-class need, not a corner case.
- **Non-Python and non-ORM authoring layers (#63).** A Swift/TypeScript
  package, a reflected database with no ORM models, or the Django adapter
  (#139, which translates `Model._meta` rather than ORM relationships) all
  need to *hand the engines a manifest* rather than derive one from Python
  annotations. The serialized JSON is the natural interchange format.

The machinery to support this already exists and is exercised:

- `DataMap.from_payload(data)` already migrates forward, validates, and
  returns a `DataMap` — it does not care whether the payload came from
  `to_payload()` or from a human/tool.
- `resolve_subject_graph_from_fk(data_map, metadata)` already builds the
  `SubjectGraph` from foreign-key constraints on a `MetaData`, with no ORM
  registry, producing a graph identical in shape and guarantees to the
  ORM-resolved one. The Django adapter (#139) already drives every engine
  this way.

So the decision is not "build new capability" but "make a supported promise
about capability we already ship", and reconcile the now-stale
*never authored* wording. Behaviour is API here (ADR 0003), so the parity
between the two paths is a contract, not an implementation detail.

## Decision

**The serialized manifest is a supported authoring and import format, not
only a derived snapshot.** A `DataMap` may be produced by `collect_data_map`
*or* hand-written / generated by another layer and loaded via
`DataMap.from_payload`. Both are first-class inputs to the engines.

### Authored-manifest contract surface

An authored manifest is the **same shape** that `from_payload` already
accepts and validates — there is no second schema. It is a JSON object:

- `DataMap` — `schema_version: int` (the `MANIFEST_SCHEMA_VERSION` the
  payload is written under; required by the migrator) and `tables: array`.
- `TableEntry` — `name` (required, non-empty), `subject_link` (optional;
  `None` until declared, but graph resolution refuses a PII-holding table
  that lacks one), `columns` (optional, defaults to empty).
- `ColumnEntry` — `name` (required, non-empty) and `spec` (required).
- `SubjectLink` — `path` (required; `""` marks the subject table) and
  `subject_id_column` (optional, defaults to `"id"`; only meaningful on the
  subject table itself).
- `PiiSpec` — `category` (required); `erasure` (optional, defaults to
  `DELETE`); `retention` (optional, but **required** when `erasure` is
  `RETAIN` — the validator enforces it); `legal_basis`, `purpose`,
  `description` (all optional).

`extra="forbid"` holds on every model, so an authored manifest with a
misspelled or unknown field is rejected, not silently ignored.

### How an authored manifest reaches execution

Identical to the derived path past the load step — no new engine code:

1. Load: `data_map = DataMap.from_payload(payload)`.
2. Build the graph from foreign keys over a reflected or hand-built
   `MetaData`: `graph = resolve_subject_graph_from_fk(data_map, metadata)`.
   (The ORM-only `resolve_subject_graph(data_map, registry)` remains the
   path for callers who *have* a registry.)
3. Drive the unchanged `Exporter`, `ErasurePlanner`, `ConsentLedger`,
   `Rectifier`, etc. with that `(data_map, graph)` pair.

### Behaviour-parity guarantee (widened SemVer, ADR 0003)

For the same logical schema, the **authored manifest + FK reflection** path
must produce **byte-identical** erasure and export results to the
**annotation-derived + ORM** path. Same FK-safe deletion order, same hop
chains, same `fully_pii_owned` classification, same exported records. The
authored path is not "best effort"; it is the same behaviour reached by a
different door. This parity is API under ADR 0003 — a divergence is a MAJOR
break — and is pinned by a property test (issue #71 implements it).

### `MANIFEST_SCHEMA_VERSION` is not bumped by this decision

Authoring needs no field the derived path did not already serialize: the
authored manifest is the existing shape. So this ADR makes **no schema
bump** and adds no migration branch. (The next bump arrives separately, with
composite subject keys — #129.)

### Validation and error semantics for hand-authored manifests

`from_payload` is the single, loud gate — hand-authored payloads get exactly
the guarantees a derived payload gets:

- A structurally invalid payload (missing required field, wrong type, an
  unknown field under `extra="forbid"`, a `RETAIN` spec with no
  `RetentionPolicy`) raises `ManifestError`.
- A payload whose `schema_version` is **newer** than the installed library
  fails loudly with upgrade guidance — never a silent best-effort parse.
- A payload from an **older** schema version is migrated forward and is
  **never rejected** (ADR 0003). An authored manifest snapshotted today
  loads on every future effaced.
- Graph-level coherence (a missing/ambiguous `subject_link("")`, a path that
  does not terminate at the subject table, FK cycles, a PII-holding table
  with no link) is caught at `resolve_subject_graph_from_fk` time as a
  `SubjectResolutionError`, exactly as for the derived path.

This is a wording/promise decision and a parity contract; it does not change
*what gets deleted or exported* for any existing input, so it carries no
behaviour-change SemVer treatment of its own.

## Consequences

- **Easier:** manifest-driven execution (#71) and non-Python / non-ORM
  authoring layers (#63) have a documented, stable contract to target. The
  reflected-schema and Django (#139) flows are now first-class, not
  undocumented side effects.
- **Harder / the price:** the byte-identical parity between the authored+FK
  and derived+ORM paths is now a guarantee we must hold and regression-test
  forever — a property test (#71) pins it, and any drift is a MAJOR break
  under ADR 0003. The authored manifest is also a new way for a human to get
  the *coherent-but-wrong* manifest (a valid shape that misrepresents the
  schema); `from_payload` and graph resolution catch structural and
  reachability errors, but effaced still ships mechanisms, not a
  determination that an authored manifest is correct or complete.
- **Wording reconciled:** the `DataMap` docstring and the docs pages that
  said *derived, never authored* are updated to *derived or authored* in the
  same change, so no rule or doc claims the format is snapshot-only.
